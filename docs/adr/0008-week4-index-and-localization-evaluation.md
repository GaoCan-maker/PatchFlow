# ADR 0008：基础提交索引与定位金标隔离

## 状态

已采用，第四周。

## 背景

PatchFlow 需要在不改变第三周三条 baseline 的前提下，先实现可解释且可消融的仓库定位。索引必须经过 Runtime 的路径策略，不能直接遍历宿主源码；评测金标不能混入 Agent 可见的任务输入。DockerRuntime 对普通命令和文件读取的输出有上限。

## 决定

1. 首版只索引 Git 已跟踪的 Python 文件，使用标准库 AST 获取定义、导入和调用名称。文件内容、数量、行数与 Git 枚举输出均受限；枚举被截断时失败，单文件跳过时在索引里记录路径。
2. 索引仅允许在干净的基础提交建立。缓存默认关闭；显式启用时，键包含仓库位置、基础提交、语言适配器版本和索引配置，JSON 文件原子替换。候选补丁后不得复用基础索引来代表当前工作区。
3. 定位器将每个原始特征、最终贡献和支持证据写入结构化输出。Issue、源码搜索、traceback、失败测试导入关系、符号名称各有开关。测试文件先验是单独显式列出的负向贡献。
4. 定位评测单独在 Docker 中运行；金标文件只由评测器读取。报告同时保存文件级、符号级 Top-K/MRR 和五组留一消融。第三周 baseline 的工具集合保持不变；第五周状态机再接入定位结果。
5. 仓库地图和 AST 符号查询先作为接收预建索引的只读工具交付，参数及实际结构化输出均受限；在候选补丁后不得将基础提交索引称为实时工作区状态。

## 结果和局限

该边界便于在不调用模型的情况下审计定位分数，避免把金标送入模型上下文，也避免候选间缓存污染。代价是大型仓库可能因上限被拒绝，静态调用名无法代表真实动态调用图，当前两题烟测不足以评估泛化或可靠比较消融。后续需要多仓库、多文件任务和修复前公开失败轨迹；补丁后的增量索引也尚未实现。
