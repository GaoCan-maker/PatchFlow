# ADR-0004：完整补丁与流式受限观察

- 状态：已接受
- 日期：2026-09-21
- 决策者：项目维护者

## 背景

普通 `git diff <base>` 不包含未跟踪的新文件。如果 Agent 新增模块，最终补丁将无声遗漏它。另一方面，先用 `communicate()` 收集完整 Docker CLI 输出再截断，即使返回给 Agent 的文本有限，宿主进程仍可能被海量输出占用内存。

## 候选方案

### 方案 A：把所有文件 `git add -N` 后生成 diff

实现简短，但会修改工作区索引状态，也可能把测试缓存等未跟踪文件纳入候选。

### 方案 B：单独枚举未跟踪文件并生成 new-file patch

通过 Git 的 NUL 分隔文件列表识别未忽略新文件，对每个文件使用 `git diff --no-index --binary` 与空设备比较，不改变索引。代价是多次 Git 调用和总 patch 大小检查。

## 决策

采用方案 B，与已跟踪文件 diff 合并。任何 Git 控制输出或合并结果超过预算都显式失败，禁止输出无法应用的截断补丁。

Docker CLI 标准输出和错误输出改为异步分块读取、增量 UTF-8 解码以及有界头尾缓存；保留原始字符总数和截断标志，内存开销随配置上限而不是命令总输出增长。

## 后果与限制

- 常规新文件会进入最终 patch，并可在 reset 后重新应用。
- `.gitignore` 忽略的文件不会自动进入补丁；特殊 Git 引号转义路径仍需独立处理。
- Docker 任务的大输出不会被完整缓存于宿主进程；LocalRuntime 仍使用旧读取实现，仅限可信仓库。
- 超大 diff 会明确失败，需要后续支持可审计的大型 artifact 或提高受控预算。

## 重新评估条件

当需要支持大型二进制文件、非常规文件名、显式包含 ignored 文件，或超大任务补丁存储时，重新设计补丁生成与 artifact 流程。
