# ADR 0010：候选独立工作区与验证金字塔

## 状态

已接受，适用于第六周实现。

## 背景

第五周的 Agent 在单个 Runtime 工作区中依次应用候选、运行测试和回滚。这个模型能够表达失败反思，但不能同时比较多个补丁；一个候选的工作区状态也可能影响下一候选。项目设计要求支持有限宽度 Candidate Branching 和从低成本到高成本的验证层级。

## 决策

1. 每个候选从干净的同一 `base_commit` 创建独立 Git 副本。
2. 候选副本通过 `RuntimeFactory` 创建对应的 LocalRuntime 或 DockerRuntime。
3. 候选补丁先按规范化文本摘要去重，再消耗工作区和测试预算。
4. 候选验证由 `VerificationPyramid` 顺序执行 V0 到 V5，并在第一处失败时早停。
5. 测试完成后重新比较 Runtime diff，测试副作用导致候选硬失败。
6. 选择器先执行硬过滤，再使用修改文件数、耗时和稳定 ID 做确定性排序。
7. 没有完整通过必需验证的候选时，不输出已验证成功的候选。

## 备选方案

### 共享一个工作区并依次 reset

实现简单，但候选失败、未跟踪文件和测试副作用容易跨候选泄漏，不满足候选隔离要求。

### Git worktree

可以减少复制成本，但候选生命周期会修改源仓库的 worktree 元数据，跨平台清理和 Docker 挂载边界更复杂。当前版本使用独立本地 clone，后续可以在基准测试证明磁盘成本过高时替换实现。

### 只运行完整测试

可以减少选择规则，但会让明显语法错误的候选占用完整测试时间，不能验证验证金字塔的效率假设。

### 使用 LLM Judge 选最终补丁

模型可以补充代码审查意见，但不能推翻语法失败、目标测试失败或回归失败。因此第六周只使用确定性信号做硬选择，Judge 留到后续平局研究。

## 后果

正面结果：候选之间拥有清晰的状态边界，验证结果带候选 ID，失败候选可被保留为研究证据，并且低成本检查可以提前节省完整测试资源。

代价：每个候选需要额外磁盘、Git 克隆和 Runtime 初始化成本；Docker 并发必须根据宿主机资源限流；当前实现仍是一层有限宽度搜索。

## 重新评估条件

当 MicroSWE 或 SWE-bench 子集显示本地 clone 成为主要成本，或者需要跨轮父候选搜索时，重新评估 Git worktree、overlayfs 和候选快照方案。
